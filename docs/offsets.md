# Offsets, signatures and schema fields

Every offset the code uses, where it came from, and how it was proven. The rules are in `CLAUDE.md` §7: never change
an offset without a diagnostic, keep the old value as a comment, flag it as **OFFSET CHANGED**.

**The standing proof is the startup diagnostic** (`app/diagnostics`): every launch, and `cs2_external.exe --diag` on its
own, checks the build number, the interfaces, every signature and every schema field against the running game. After
a CS2 update, run `--diag` first.

## Interfaces (`offsets::interfaces`, found at runtime by `game/interfaces`)

`CreateInterface` is exported by every module that registers interfaces. We can't call it, so `game/interfaces` reads
its first instruction, `4C 8B 0D disp32` (`mov r9, [rip + s_pInterfaceRegs]`), walks the `InterfaceReg` list
(`create` +0x0, `name` +0x8, `next` +0x10), and decodes each create function, `48 8D 05 disp32 C3`
(`lea rax, [rip + instance]; ret`).

| Interface | Module | Instance RVA | Proof |
|---|---|---|---|
| `Source2Client002` | client.dll | `0x255C3A0` | Walk = dump |
| `Source2EngineToClient001` ("EngineClient") | engine2.dll | `0x61FFF0` | Walk = dump |
| `SchemaSystem_001` | schemasystem.dll | `0x76710` | Walk = dump |
| `InputSystemVersion001` | inputsystem.dll | `0x46BC0` | Walk = dump = `dwInputSystem` |

2026-10-06: the walk matched `interfaces.json` for **all 59 interfaces** of client (9), engine2 (34), schemasystem (1),
inputsystem (2) and tier0 (4) (checked with the scratch script; the tool checks the four above). Every create function
had the lea/ret shape.

"GameEntitySystem" is **not** a registered interface in CS2. The entity system is the global `dwGameEntitySystem`.

## Signatures (`offsets::signatures::kClient`, client.dll `.text`)

Every signature is a RIP-relative instruction: target = match + 7 + disp32 (disp32 at +3), plus `add`. Found by hand
2026-10-06 against the live client.dll of build 14189: list every RIP-relative reference to each dumped global, then
pick a pattern that skips call targets and struct offsets (the parts that change between builds). Each one matches only
places that resolve to exactly the dumped value.

| Global | Pattern | Hits | Notes |
|---|---|---|---|
| `dwEntityList` | `48 89 0D ? ? ? ? E9 ? ? ? ? CC` | 1 | the store of the entity system; the a2x-style `48 89 35 ? ? ? ? 48 85 F6` no longer hits |
| `dwLocalPlayerController` | `48 8B 05 ? ? ? ? 41 89 BE` | 1 | a2x-style, still works |
| `dwLocalPlayerPawn` | `48 8D 05 ? ? ? ? C3 CC CC CC CC CC CC CC CC 40 53 56 41 54 41 56 41 57` | 1 | prediction getter, then `add = 0xF8` (= dump `dwLocalPlayerPawn - dwPrediction`); the a2x-style `... 48 83 EC ? 8B 0D` tail hits two other functions now |
| `dwViewMatrix` | `48 8D 0D ? ? ? ? 48 C1 E0 06` | 1 | a2x-style |
| `dwGlobalVars` | `48 89 15 ? ? ? ? 48 89 42` | 1 | a2x-style |
| `dwGameRules` | `48 89 1D ? ? ? ? FF 15 ? ? ? ? 84 C0` | 2 | both the same global; the resolver accepts agreeing matches |
| `dwPlantedC4` | `4C 89 35 ? ? ? ? EB ? 48 8B 05` | 1 | the a2x-style `48 8B 15 ? ? ? ? 41 FF C0` no longer hits |
| `dwCSGOInput` | `48 89 05 ? ? ? ? 0F 57 C0 0F 11 05` | 1 | a2x-style |

The code uses the **dump values**; the signatures are the cross-check (and the way to find new values after an update).

## Entity list (`offsets::layout::kEntity*`, `kIdentity*`, `kHandle*`; code: `game/handle`, `game/entities`)

Proven 2026-10-06 by resolving the local player's `m_hActiveWeapon` handle (`0x1B182E6`, index 742) by hand:

- Chunk pointer: `entity_system + 0x10 + (index >> 9) * 8` (as CLAUDE.md said). The stored pointers end in `...008`.
- **Identity size is `0x70`**, not `0x78`: `identity = chunk + (index & 0x1FF) * 0x70`. With 0x78 the read gave 0.
  Cross-check: the local pawn's own identity pointer (`pawn + 0x10`) sits at chunk 0 + 205 * 0x70 exactly.
- `identity + 0x0` is the entity pointer.
- **`identity + 0x10` holds the whole handle** (`0x1B182E6`), not the serial alone: compare it with the handle (or
  compare `>> 15` on both sides).
- `identity + 0x20` points to the designer name (`weapon_ak47`).

In code since Phase 3 (`offsets::layout`). Phase 3 proof (2026-10-06, build 14189, de_mirage bot match, read-only
script, then `cs2_external.exe --live`):

- Entity 0 is `worldent`; indices **1..20** held the 20 players' controllers, designer name `cs_player_controller`
  (the next player index, 21, was empty). Player controllers are looked for at 1..maxClients (64).
- Every controller's `m_hPlayerPawn` resolved (serial check passing) to a pawn with health 100, life state 0, the
  controller's team, a finite origin and a view offset of ~64 units.
- Every pawn's `m_hController` equals its controller's own handle (e.g. `0x8E0001` for index 1): the identity handle
  layout holds in both directions.
- A pawn's own designer name is `c_cs_player_for_precache` (entity 67), not `cs_player_pawn`: don't find pawns by
  name.
- Local player: `dwLocalPlayerController` = the index-1 controller (`bigh18valorant`), whose pawn = `dwLocalPlayerPawn`.

## CGlobalVars (`offsets::layout::kGlobals*`, code: `game/globals`)

`client.dll + dwGlobalVars` holds a pointer to the struct. Found 2026-10-06 (build 14189) by reading `0x200` bytes
twice, 2.0 s apart, in a bot match:

| Offset | Field | Evidence |
|---|---|---|
| `0x00` | realtime (float) | advanced by 2.001 in 2.0 s |
| `0x04` | framecount (int32) | advanced by 676 (≈ the game's FPS × 2) |
| `0x08` / `0x34` | frametime (float) | ~0.005 (not used) |
| `0x10` | maxClients (int32) | 64 |
| `0x1C` | interval_per_tick (float) | 0.015625 = 1/64 |
| `0x30` | curtime (float) | advanced by 2.001; = tickcount × interval (399512 × 1/64 = 6242.4) |
| `0x44` | tickcount (int32) | advanced by 128 (64 tick × 2 s) |
| `0x48` / `0x4C` | another tick + its time (not used) | +128 / +2.0 |
| `0x188` | map name (`const char*`) | "de_mirage" (`0x180` points to "maps/de_mirage.vpk") |

The layout CLAUDE.md used to call "typical" (curtime `0x10`, maxClients `0x18`) is wrong for this build: `0x10` reads
64. `read_globals` reads `0x190` bytes in one go, then the map name.

## View matrix (`client.dll + dwViewMatrix`, code: `game/view`)

16 floats inline at the global (no pointer). Read 2026-10-06 in a bot match: non-zero, finite, with the bottom row
`[0.792, -0.601, -0.106, 1821.5]`, i.e. the camera's forward axis and a translation, as row-major predicts (clip.w =
row 3 · (x, y, z, 1)). `ViewMatrix::is_sane` rejects all-zero and non-finite matrices. Projection is Phase 4.

## Bones (`offsets::layout::kModelStateBones`, `kBoneStride`; code: `game/bones`, indices in `maths/skeleton.h`)

Not in any dump. Found 2026-10-06 (build 14189, de_mirage bot match) with a read-only script:

- pawn + `m_pGameSceneNode` → scene node (a `CSkeletonInstance`) + `m_modelState` (`0x140`) + **`0x80`** → pointer to
  the bone array. Non-null for all 20 pawns.
- Each bone is **32 bytes**: `Vector position` (12), `float scale` (read 1.0 for every bone), `Quaternion rotation`
  (16).
- Positions sit on the pawn: bone 0 at the feet (≈ the origin), the highest bones ~64 units up, nothing more than
  ~22 units sideways, except bone 27, which is ~1000 units straight ahead of the face (a look-at target).
- Joint indices mapped from each bone's position in the bot's own frame (forward / left / up from its feet, using its
  eye yaw), identical on CT (Kev, Specialist) and T (Blackwolf, Skullhead) models:

| Index | Joint | Kev (standing): fwd / left / up |
|---|---|---|
| 0 | root (feet) | 0 / 0 / -1.5 |
| 1 | pelvis | -3.7 / 5.4 / 37.1 |
| 2, 3, 4 | spine | up 38.1, 42.1, 46.7 |
| 5 | neck | -2.1 / 3.5 / 53.0 |
| 6 | **head** | 0.6 / 1.8 / 58.7 |
| 7 | face / eyes (27 looks from here) | 4.7 / 0.1 / 62.4 |
| 9, 10, 11 | left shoulder, elbow, hand | left +9.7 → hand 17 forward (holding the gun) |
| 13, 14, 15 | right shoulder, elbow, hand | left -5.3 → hand 16 forward |
| 17, 18, 19 | left hip, knee, foot | up 33.6, 19.4, 2.9 |
| 20, 21, 22 | right hip, knee, foot | up 33.3, 17.8, 3.7 |

The often-published CS2 list (legs at 22-27) does not match this build. `read_bones` reads bones 0..22 (736 bytes, one
read) and rejects the array if a bone is non-finite or > 200 units from the feet.

Proof in the tool: `--diag` "Bones (model state + 0x80)": all alive players have bones, head bone 30-80 units above
the feet (read: 20 of 20, 52 to 60). Screenshot 2026-10-06: every skeleton drawn inside its box, head circle on the
head, feet on the box's bottom edge.

## Projection (`maths/projection`)

`dwViewMatrix` is row-major (see "View matrix" above). Proven 2026-10-06 with the local player's eye position
(origin + `m_vecViewOffset`) and view angles (`dwViewAngles` = `m_angEyeAngles` = (6.105, -37.210, 0)): the point
1000 units along forward = (cos p · cos y, cos p · sin y, -sin p) projected to (960.0, 540.0) on 1920x1080, at 100,
1000 and 5000 units, with w equal to the distance. 100 units up → y 467.6 (up the screen); 100 units right (yaw - 90°)
→ x 1032; 1000 units behind → w = -1000. So: pitch positive = looking down, screen y grows downwards, w < 0 behind.
The matrix and points are in `tests/maths/test_projection.cpp`.
